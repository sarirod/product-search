# חיפוש חכם בקטלוג מוצרים

חיפוש בקטלוג של 1,000 מוצרים בעברית, באנגלית ובשילוב של שתיהן. אפשר לחפש לפי שם המוצר וגם לפי **הצורך**, למשל "משהו שיעזור לנקות שערות של כלב מהספה".

- **אתר חי:** https://product-search-ogr0.onrender.com
- **קוד:** https://github.com/sarirod/product-search

**טכנולוגיות:** PHP 8.3 (בלי framework), PostgreSQL + pgvector (Neon), Gemini embeddings, ‏HTML/CSS/JS נקי. הפריסה ב-Render (Docker).

## איך זה עובד

```
דפדפן  ──GET /api/search.php?q=…──►  PHP
                                      ├─ 1. משמעות: Gemini הופך את השאילתה לווקטור (עם cache ב-DB),
                                      │     ו-pgvector מוצא את המוצרים הקרובים ביותר (cosine)
                                      ├─ 2. מילות מפתח: התאמה לתחילת מילה בשם / מותג / קטגוריה / צרכים / תיאור
                                      └─ 3. מיזוג שתי הרשימות ב-Reciprocal Rank Fusion  ──►  JSON
```

- **חיפוש לפי משמעות** מטפל ב"אייפון" (המילה iPhone לא מופיעה בקטלוג בכלל), ב"מתנה למישהו שאוהב לבשל" ובשילוב שפות.
- **חיפוש מילות מפתח** מטפל בשמות מדויקים, במותגים ובמספרים ("Air Fryer גדול", ‏"KitchenAid").
- **אם Gemini לא זמין** (נגמרה המכסה, תקלת רשת, מפתח שגוי), האתר ממשיך לעבוד במצב מילות מפתח בלבד ומציג על כך הערה עדינה.

## הרצה מקומית

דרישות: PHP 8.3 עם ההרחבות `pdo_pgsql`, `curl` ו-`mbstring`, מסד PostgreSQL עם pgvector (למשל Neon בחינם), ומפתח Gemini מ-[Google AI Studio](https://aistudio.google.com/apikey).

```bash
cp .env.example .env          # ממלאים DATABASE_URL ו-GEMINI_API_KEY (הקובץ ב-.gitignore)
php bin/migrate.php           # יוצר טבלאות (אפשר להריץ שוב ושוב)
php bin/import.php            # טוען את הקטלוג ומחשב embeddings
php -S localhost:8000 -t public
```

**בדיקות:**
```bash
php tests/run.php                   # ‏69 unit tests, בלי DB ובלי מפתח
php tests/relevance.php --verbose   # מבחני רלוונטיות מול ה-DB וה-API האמיתיים
php tests/explore.php               # 87 חיפושים לבדיקה ידנית (או: php tests/explore.php "שאילתה")
```

### מבנה הפרויקט

```
public/            האתר: index.html, ‏app.js, ‏styles.css, ו-api/ (search.php, health.php). רק התיקייה הזו חשופה לרשת
src/Search.php     החיפוש ההיברידי: וקטורים, מילות מפתח, סף רלוונטיות ו-RRF
src/Text.php       נרמול טקסט, תחיליות בעברית, regex למילות מפתח ותיקון כתיב
src/Embedder.php   קריאות ל-Gemini (cURL, בלי SDK)
src/Catalog.php    קריאה ואימות של קבצי ה-CSV
bin/               migrate.php (יצירת טבלאות), ‏import.php (טעינת הקטלוג וחישוב embeddings)
tests/             run.php (unit), ‏relevance.php (רלוונטיות), ‏explore.php (87 חיפושים)
data/              הקטלוג המקורי, מחירים והעשרה
```

### טעינת הנתונים
`bin/import.php` קורא שלושה קבצים ומאחד אותם לפי `id`:

| קובץ | מה יש בו |
|---|---|
| `data/catalog.csv` | הקטלוג המקורי, **ללא שינוי** |
| `data/prices.csv` | מחירים משוערים (ראו "החלטות") |
| `data/enrichment.csv` | שורת "צרכים ושימושים" לכל מוצר (ראו "החלטות") |

- **אימות לפני כתיבה:** id תקין וייחודי, שדות חובה, תמונות ב-https, מחיר חיובי. אם יש בעיה, הייבוא נעצר עם רשימה של כל השגיאות ולא כותב חצי קטלוג.
- **אידמפוטנטי:** לכל מוצר נשמר `content_hash`. בהרצה חוזרת מתעדכנים רק מוצרים שהשתנו, ו-embedding מחושב מחדש רק למוצר שהטקסט שלו השתנה. מוצר שנמחק מה-CSV נמחק גם מה-DB.
- **עמידות:** ה-embeddings מחושבים ב-batches של 50, וכל batch נשמר בנפרד. אם יש עצירה באמצע, הרצה נוספת ממשיכה מאותה נקודה. על מגבלת קצב לדקה הסקריפט מחכה ומנסה שוב. כשהמכסה היומית נגמרת הוא עוצר מיד ומסביר מתי לנסות שוב.

## החלטות ונימוקים

**חיפוש היברידי (משמעות + מילות מפתח).** כל שיטה לבד נכשלת על חלק מהדוגמאות בתרגיל:
- מילות מפתח לבד לא ימצאו "אייפון", כי בקטלוג הוא רשום כ"סמארטפון חכם 6.1 אינץ' 128GB" עם המותג Apple.
- וקטורים לבד חלשים יותר בהתאמה מדויקת לשם, מותג ומספרים.

את שתי הרשימות ממזגים ב-**RRF** (‏k=60). זו שיטה פשוטה ויציבה שלא דורשת לכוונן משקלות בין ציונים שאינם ברי השוואה.

**העשרה של "צרכים ושימושים".** הדרישה היא לחפש לפי צורך, ולא רק לפי תיאור. בתיאורים בקטלוג אין משפטים כמו "מתאים למי שיש לו כלב". לכן לכל מוצר נוספה שורה קצרה (נוצרה בעזרת Claude) שמתארת למי הוא מתאים ואיזו בעיה הוא פותר, בעברית עם מילות מפתח באנגלית. השורה נכנסת לטקסט שעובר embedding ולחיפוש מילות המפתח. היא נשמרת בקובץ נפרד, כך שהקטלוג המקורי נשאר נקי וקל להחליף או לשפר את ההעשרה.

**מחירים משוערים.** בקטלוג אין עמודת מחיר, אבל נדרש להציג מחיר. נוצרו מחירים ריאליים בש"ח לפי סוג המוצר, המותג והמפרט, ונבדקו בטווחים (מינימום ומקסימום) לכל תת-קטגוריה. הם נשמרים ב-`data/prices.csv`, ובאתר מוצגת הערה שהמחירים משוערים.

**PostgreSQL + pgvector ולא MySQL.** החיפוש הסמנטי צריך לחשב מרחק בין וקטורים בתוך ה-DB. ב-pgvector זו פעולה מובנית (`<=>`). ב-MySQL הייתי צריכה לשלוף את כל הווקטורים ל-PHP ולחשב שם. Neon נותן Postgres מנוהל וחינמי עם pgvector, באזור Frankfurt.

**בלי אינדקס וקטורי (HNSW).** עם 1,000 מוצרים, סריקה מלאה לוקחת כ-3ms בצד השרת, והיא **מדויקת**. אינדקס מקורב היה מוסיף מורכבות בלי תועלת בגודל הזה.

**מילות מפתח עם regex לתחילת מילה, ולא pg_trgm.** בעברית מילים מקבלות תחיליות: "**מה**ספה", "**ל**כלבים". pg_trgm נשקל ונדחה: חלוקת המילים שלו תלויה ב-locale של השרת, ועל עברית ההתנהגות לא צפויה. במקום זה:
- השאילתה מנורמלת (אותיות קטנות, הסרת ניקוד, איחוד גרשיים) ומפורקת למילים. מילות מילוי ("משהו", "של", "שאוהב") מושמטות.
- לכל מילה נבנה regex שמתאים לתחילת מילה, עם עד 2 אותיות תחילית ובלי סיומת רבים.
- מילים קצרות (עד 3 אותיות בעברית, עד 4 באנגלית) חייבות להתאים כמילה שלמה עם סיומת נטייה בלבד. אחרת "לגו" מתאים ל"לגוף", ו-"baby" מתאים למותג BaByliss.
- התאמה בשם או במותג שווה יותר מהתאמה בתיאור. מוצר שהמילים נמצאו רק בתיאור הארוך שלו מוצג רק אם גם החיפוש לפי משמעות תומך בו.
- מילה באנגלית שלא קיימת בקטלוג מתוקנת למילה הקרובה ביותר מהקטלוג (מרחק עריכה 1-2, למשל "dysn" ← "dyson").

**סף רלוונטיות.** כדי ששאילתת ג'יבריש תחזיר "לא נמצאו תוצאות" ולא 24 מוצרים אקראיים, נשמרות רק תוצאות וקטוריות שעוברות סף דמיון מוחלט, והן גם צריכות להיות קרובות לתוצאה הטובה ביותר (סף יחסי). את הערכים קבעתי לפי ההתפלגות על השאילתות שבבדיקות.

**Cache לשאילתות.** וקטור של שאילתה נשמר בטבלה `query_embeddings`. כך חיפוש חוזר לא פונה ל-Gemini, וזה גם מהיר יותר וגם חוסך מכסה.

**חיפוש ב-Enter או בלחיצה, ולא בכל הקשה.** כל שאילתה חדשה עולה קריאת API. חיפוש בכל הקשה היה שורף מכסה ומציג תוצאות מהבהבות על מילים חלקיות.

**PHP בלי framework.** בהיקף הזה framework היה מוסיף בעיקר קבצים. הקוד מחולק למחלקות קטנות: `Text`, ‏`Embedder`, ‏`Search`, ‏`Catalog` ו-`Db`.

**UX:** תמיכה מלאה ב-RTL, תצוגה מותאמת למובייל, כרטיסי skeleton בזמן טעינה, מסך "אין תוצאות" עם הצעות לחיפוש, מסך שגיאה עם "נסו שוב", ושמירת `?q=` בכתובת כך שאפשר לשתף חיפוש והכפתור "אחורה" עובד. בקשה קודמת מבוטלת כשמתחילים חיפוש חדש. בתמונה שלא נטענת מוצגת תמונה חלופית. הנתונים נכנסים ל-DOM רק דרך `textContent`, כדי למנוע XSS.

**אבטחה:** כל השאילתות ל-DB הן prepared statements. רק התיקייה `public/` חשופה לרשת. המפתחות נמצאים רק ב-`.env` המקומי וב-Environment Variables של Render, ואף פעם לא במאגר.

## מגבלות ושיפורים אפשריים

- **מחירים משוערים.** בפרויקט אמיתי הם יגיעו ממערכת המלאי.
- **מכסת Gemini החינמית: 1,000 embeddings ביום.** חישוב מחדש של כל הקטלוג מנצל את כל המכסה היומית, וכך גם שינוי בטקסט שעובר embedding לכל המוצרים. שינוי חלקי מחושב רק על המוצרים שהשתנו. בפרודקשן הייתי עוברת לתוכנית בתשלום (חישוב כל הקטלוג עולה סנטים בודדים).
- **ההעשרה נוצרה במודל שפה.** היא נבדקה במדגם ובמבחני הרלוונטיות, אבל לא נבדקה ידנית שורה אחרי שורה.
- **שגיאות כתיב** מטופלות דרך החיפוש הסמנטי, ובאנגלית גם בתיקון מול אוצר המילים של הקטלוג. התיקון לא מוצג למשתמשת, ואפשר להוסיף "התכוונת ל…".
- **מוצר שלא קיים בקטלוג** מחזיר את הקרובים אליו במשמעות: "כינור" מחזיר גיטרות ויוקללה. לפעמים נכנסת גם התאמה מילולית מטעה: ב"קשת לכינור" מופיעה "מנורת רצפה קשתית", כי גם המילה וגם המשמעות קרובות ל"קשת".
- **מקלדת בשפה הלא נכונה** ("שןפיםמק" במקום "aiphone") מחזירה תוצאות חלשות במקום "אין תוצאות". ההתפלגות של ציוני הדמיון שם דומה לזו של חיפושים אמיתיים, ולכן הסף לא יכול להפריד ביניהם בלי לפגוע בהם. פתרון אפשרי: לזהות טקסט שהוקלד במקלדת הלא נכונה ולהמיר אותו.
- **אין פילטרים ומיון** (מחיר, קטגוריה, מותג), ואין עימוד מעבר ל-24 תוצאות.
- **אין rate limiting** על ה-API. בפרודקשן צריך להגביל לפי IP, כדי שאי אפשר יהיה לשרוף את המכסה.
- **בקנה מידה גדול** (מאות אלפי מוצרים) צריך אינדקס HNSW ואינדקס טקסט מלא במקום regex על כל השורות.
- **Render בחינם נרדם** אחרי זמן ללא תנועה. מוגדר פינג תקופתי ל-`/api/health.php` (שלא נוגע ב-DB), אבל הבקשה הראשונה אחרי הירדמות עדיין עלולה להיות איטית.

## עבודה עם Claude

השתמשתי ב-Claude (Claude Code) לאורך כל הפרויקט:
- תכנון הארכיטקטורה ובחירת הטכנולוגיות.
- כתיבת הקוד, הבדיקות וה-Dockerfile.
- יצירת המחירים המשוערים ושורות ההעשרה.
- הרצת הבדיקות ואבחון תקלות.

**איך בדקתי את מה ש-Claude ייצר:**
- **נתונים:** ולידציה אוטומטית ב-`Catalog::load` (בדיוק 1,000 id שתואמים לקטלוג, אין מחיר ריק או לא חיובי, אין שורת צרכים ריקה), בדיקת טווחי מחיר לכל תת-קטגוריה, וקריאה של מדגם שורות.
- **קוד:** ‏unit tests (`tests/run.php`) ומבחני רלוונטיות עם תוצאות צפויות מראש לכל דוגמה מהתרגיל (`tests/relevance.php`). במבחנים מוגדר איזה מוצר **צריך** להופיע ב-top-K, כך שלא בודקים רק ש"משהו חזר".
- **הרצה אמיתית:** ייבוא מלא, הרצה שנייה לבדיקת אידמפוטנטיות, ודימוי של תקלות (DB לא זמין, מפתח שגוי).
- **סודות:** סריקה של היסטוריית git לפני ההעלאה, לוודא שאף מפתח לא נכנס.

**החלטות של Claude שבחנתי, ושיניתי או אישרתי:**
1. **חיפוש לפי צורך.** התוכנית הראשונה של Claude הסתמכה על embeddings בלבד כדי להבין צרכים. בבדיקת התוכנית שאלתי אם זה באמת מכסה חיפוש לפי צורך ולא רק לפי תיאור. בדיקה של הנתונים הראתה שלמשל למברשת שמסירה שיער של חיות מחמד אין בתיאור שום אזכור של "כלב" או "ספה". בעקבות זה הוספנו את שכבת ההעשרה (`data/enrichment.csv`).
2. **pg_trgm.** בתוכנית המקורית, חיפוש מילות המפתח היה מבוסס על `word_similarity` של pg_trgm. בשלב המימוש החלפנו אותו ב-regex לתחילת מילה עם טיפול בתחיליות, כי טריגרמים בעברית תלויים ב-locale ולא מטפלים ב"מהספה" מול "ספה".
3. **ניסיונות חוזרים על מכסה יומית.** מנגנון ה-retry של Claude ניסה שוב על כל שגיאת 429, אבל בהרצה האמיתית התברר שחלק מהשגיאות הן מכסה **יומית**. במקרה כזה הניסיונות החוזרים רק בזבזו כמה דקות. שיניתי את הקוד כך שיזהה את סוג המגבלה ויעצור מיד עם הסבר.
4. **סף הרלוונטיות.** Claude קבע בהתחלה סף מוחלט של 0.55. בבדיקה ידנית באתר החי, החיפוש "הגדרות" החזיר 24 מוצרים אקראיים. בדיקה של המספרים הראתה שב-Gemini גם טקסטים לא קשורים מקבלים ציון של כ-0.6, ולכן הציון לבדו לא אומר הרבה. מה שמבדיל חיפוש אמיתי הוא **הפער** בין ההתאמות הטובות לשאר (ב"שואב אבק" 0.75 מול 0.63, וב"הגדרות" 0.65 מול 0.63). הכלל שונה ל"מציגים רק מוצרים שבולטים", והערכים כוילו על החיפושים האמיתיים.
5. **MySQL.** שאלתי למה לא MySQL, שאני מכירה. Claude הסביר את היתרון של חישוב מרחק וקטורי בתוך ה-DB, ובחרתי ב-Postgres עם pgvector אחרי שהבנתי את ההבדל.

**באגים שמצאתי בבדיקה ותיקנתי:**
1. **באג באידמפוטנטיות.** Claude כתב בייבוא את התנאי `WHERE products IS DISTINCT FROM EXCLUDED`. השוואה של שורה מלאה כוללת גם עמודות שלא נשלחות בייבוא (embedding, ‏updated_at), ולכן כל מוצר היה מסומן כ"עודכן" בכל הרצה. זה התגלה בבדיקה, והתנאי הוחלף בהשוואה מפורשת של העמודות הרלוונטיות.
2. **באג שלא נתפס בבדיקות ה-unit.** "iPhone 16", אחת הדוגמאות בתרגיל, החזיר שגיאה 500 באתר החי. PHP הופך מפתח מערך "16" למספר שלם, והקוד (`strict_types`) קרס. הבדיקות של Claude לא כללו שאילתה עם מספר. תוקן, ונוספה בדיקה שתתפוס את זה בעתיד. מסקנה: בדיקת ה-end-to-end על כל הדוגמאות מהתרגיל היא חובה, ולא תוספת.
3. **רעש מהתאמה מילולית חלקית.** בחיפוש "ערכת לימוד מגע לילדים" הופיע גם "מד חום מגע למצח", שהתאים רק למילה "מגע". עכשיו, תוצאה מילולית שמתאימה רק לחלק מהמילים מוצגת רק אם גם החיפוש לפי משמעות רואה בה מועמדת.
4. **באגים שנמצאו בבדיקת חקר רחבה** (`tests/explore.php`, ‏87 חיפושים). מבחני הרלוונטיות עברו, אבל הם בודקים רק את הדוגמאות מהתרגיל. לכן הרצנו עשרות חיפושים "אמיתיים" ומוזרים, וקראתי את התוצאות ידנית. זה חשף באגים שהבדיקות האוטומטיות לא תפסו: "לגו" התאים ל"לגוף", ‏"cat" ל"קטאן" (catan), ו-"baby" למסלסלי שיער של המותג BaByliss. כולם תוקנו עם בדיקה שתתפוס אותם בעתיד.
5. **התאמה רק בתיאור.** "הגדרות" עדיין החזיר 15 מוצרים, כמו מכונת לחם וגוזם זקן, כי בתיאור שלהם כתוב "3 הגדרות אורך" או "תוכניות מוגדרות". בכרטיס תוצאה, שבו רואים רק שם ומחיר, זה נראה אקראי. עכשיו מוצר שהמילים נמצאו רק בתיאור הארוך שלו מוצג רק אם גם החיפוש לפי משמעות תומך בו. זה גם ניקה רעש כמו שקיות ואקום ב"שואב אבק" ושמיכת קיץ ב"משהו לחורף".
6. **שגיאות כתיב במותגים.** "dysn" החזיר כונני NAS ולא את מוצרי דייסון, כי ה-embedding לא "מבין" שגיאת כתיב בשם מותג. נוסף תיקון של מילים באנגלית מול אוצר המילים של הקטלוג. רק מילה שלא מופיעה בקטלוג בכלל מוחלפת, כך שחיפושים תקינים לא משתנים (וידאתי זאת בהשוואה של כל 87 החיפושים לפני ואחרי).
